## 왜 필요한가

HTTP 는 **무상태**.  
서버는 “이 요청이 직전에 로그인한 그 사람인가?” 를 요청만 보고는 알 수 없다.

→ 클라이언트가 매 요청에 **식별 정보** 를 실어 보내고,  
서버가 그걸 보고 로그인·장바구니·권한을 복원한다.

---

## Cookie (쿠키)

서버가 `Set-Cookie` 로 심고, 브라우저가 이후 요청에 `Cookie` 헤더로 자동 첨부하는 **작은 이름=값** 데이터.

```text
# 응답
Set-Cookie: user=guest; Path=/; HttpOnly

# 이후 요청
Cookie: user=guest
```

### 어디에 쓰이나

| 용도 | 예 |
|------|-----|
| 세션 ID 전달 | `sessionid=...` (실제 데이터는 서버) |
| 선호 설정 | 언어, 테마 |
| (잘못된 설계) 권한·역할 자체를 쿠키 값에 | `role=admin` — 위조에 취약 |

### 보안 속성

| 속성 | 역할 |
|------|------|
| **HttpOnly** | JS 가 쿠키를 못 읽음 → XSS 로 세션 탈취 난이도↑ |
| **Secure** | HTTPS 에서만 전송 |
| **SameSite** | 크로스 사이트 요청에 쿠키를 붙일지 (CSRF 완화에 중요) |
| **Domain / Path** | 어느 호스트·경로에 붙는지 |
| **Max-Age / Expires** | 수명 |

### 클라이언트 쪽 조작

- DevTools → Application → Cookies 에서 **값 수정**  
- 요청 가로채기 후 `Cookie` 헤더 변경  

서버가 쿠키 값을 **그대로 신뢰**하면 (서명·서버 세션 없이 `role=admin` 등) 권한 상승이 된다.  
→ 연습 문제 **cookie** 계열의 전형.

## Session (세션)

**서버 쪽** 에 사용자 상태(로그인 여부, user id, …)를 두고,  
클라이언트에는 보통 **짧은 식별자(세션 ID)** 만 쿠키로 주는 방식.

```text
브라우저                         서버
   |  POST /login (id, pw)         |
   | ----------------------------> |
   |  Set-Cookie: sid=랜덤값       |  저장: sid → {user: admin, ...}
   | <---------------------------- |
   |  GET /admin  Cookie: sid=...  |
   | ----------------------------> |  sid 로 세션 조회 → 권한 판단
```

| | Cookie 에 상태 전부 | Session (+ 쿠키에 ID 만) |
|--|---------------------|---------------------------|
| 데이터 위치 | 클라이언트 | 서버 |
| 변조 | 클라이언트가 값 고치기 쉬움 | ID 추측·탈취가 이슈 |
| 서버 부하 | 낮음 | 세션 저장소 필요 |
| 로그아웃 | 쿠키 삭제 | 서버 세션 삭제 + 쿠키 삭제 |

실무·강의에서 말하는 “쿠키와 세션”은 대개  
**세션 저장 + 세션 ID 쿠키** 조합을 가리킨다.

## 흔한 취약·실수 (분석 관점)

| 패턴 | 무엇이 문제인가 | 관찰 포인트 |
|------|-----------------|-------------|
| 역할/권한이 쿠키 평문 | 값만 바꾸면 admin | Application → Cookies |
| 예측 가능한 세션 ID | 다른 사용자 세션 추측 | ID 형식·길이·랜덤성 |
| 로그인 전후 세션 ID 고정 | 세션 고정(fixation) | 로그인 전후 `Set-Cookie` 비교 |
| HttpOnly 없음 | XSS 로 `document.cookie` 탈취 | 쿠키 플래그 |
| Secure 없음 + HTTP | 중간 경로 유출 | 스킴·플래그 |
| 세션 만료·무효화 없음 | 탈취 후 장기 사용 | 로그아웃 후 옛 sid 재사용 |

### Flask 등 웹앱에서 (유닛 맥락)

- 시크릿 키 약함 → 서명 쿠키 위조 가능 (프레임워크별)  
- 세션에 민감 정보를 과다 저장  
- 권한 검사를 “페이지 숨김”에만 두고 **API/경로는 열어 둠**  

분석 순서: **소스(있을 때) → 쿠키/세션 동작 → 권한 분기 조건**.

## 연습 문제 방향

### cookie (#6)

- 설명 유형: 쿠키로 인증 상태를 관리하는 로그인  
- 접근: 로그인 전후 쿠키 변화 확인 → 값·이름에 권한 힌트가 있는지 → 변조 후 `/` 또는 admin 페이지 재요청  
- 핵심: **서버가 쿠키 값을 검증 없이 신뢰하는가**

### session-basic (#409)

- 설명 유형: 쿠키 + 세션으로 인증  
- 접근: 세션 ID 쿠키 vs 서버 저장 데이터 구분 → admin 로그인 조건이 소스/로직에 어떻게 있는지 → 세션을 어떻게 얻는지  
- 핵심: **세션에 무엇이 들어가고, 그걸 누가 설정하는가**

## 한 줄 정리

| 개념 | 한 줄 |
|------|--------|
| Cookie | 브라우저가 보관·자동 전송하는 작은 데이터 |
| Session | 서버가 보관하는 상태; 보통 쿠키로 ID 만 전달 |
| 분석 | “이 값이 클라이언트가 고칠 수 있는가?” / “서버가 다시 검증하는가?” |
